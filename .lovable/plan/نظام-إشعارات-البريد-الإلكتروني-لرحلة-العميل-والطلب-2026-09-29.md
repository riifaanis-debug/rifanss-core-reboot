# نظام إشعارات البريد الإلكتروني لرحلة العميل والطلب

البريد قناة إضافية بجانب الإشعارات داخل الموقع. لا تغيير على OTP أو الدخول أو مفتاح Resend أو نصوص العقود/السندات/الفواتير أو الأتعاب أو التصميم العام.

## 1. كيف يعمل (موثوق من الخادم)
- لا يعتمد الإرسال على المتصفح. عند حدوث التغيير فعليًا في القاعدة (إنشاء طلب، تغيير حالة، إنشاء عقد/سند/فاتورة، حفظ توقيع، إكمال التسجيل) تسجّل القاعدة نفسها حدث البريد في سجل `email_events` بحالة «بانتظار الإرسال» ضمن نفس العملية.
- القاعدة تستدعي مسار الخادم تلقائيًا لمعالجة الحدث (باستدعاء خادمي موقّع بسر داخلي)، والخادم يقرأ البيانات من القاعدة بنفسه ويرسل عبر Resend.
- احتياط: أي حدث بقي «بانتظار الإرسال» أو «فشل» قابل لإعادة المحاولة تتم معالجته دوريًا كل بضع دقائق، مع حد أقصى للمحاولات.
- بريد العميل = المسجّل في حسابه؛ بريد المسؤول = ADMIN_EMAIL الحالي؛ المرسل «ريفانس المالية <no-reply@mail.rifanss.com>».

## 2. منع التكرار
- مفتاح فريد: (الحدث + معرّف العنصر + المستلم: عميل/مسؤول). نفس الحدث يرسل رسالة واحدة للعميل وواحدة للمسؤول فقط.
- حالات الطلب: يُسجَّل الحدث فقط عند تغيّر الحالة فعليًا؛ حفظ نفس الحالة لا يُنشئ حدثًا.
- المستند البديل له معرّف جديد فيُرسل له بريد جديد.

## 3. فشل البريد
- فشل Resend لا يلغي العملية ولا يظهر للعميل. يُسجَّل «فشل» مع سبب مختصر آمن.

## 4. سجل الإرسال `email_events`
- الحقول: event، entity_id، recipient_role، status، error، attempts، created_at، sent_at.
- لا يُخزَّن محتوى البريد ولا عناوين أو أسرار أو بيانات حساسة.
- لا وصول له من المتصفح إطلاقًا.

## 5. الأحداث
| الحدث | إلى |
|---|---|
| إكمال التسجيل فعليًا (عند حفظ بيانات الحساب المكتملة، لا عند إرسال OTP أو التحقق منه) | العميل + المسؤول |
| تقديم طلب (أي نوع) | العميل + المسؤول (بدون مرفقات أو روابط ملفات؛ زر «عرض الطلب» يتطلب دخول المسؤول) |
| تحت الإجراء / قيد التنفيذ | العميل |
| نقص مستندات (المستندات والملاحظة فقط إن سُجلت) | العميل |
| رفع العميل للمستندات المطلوبة | المسؤول |
| إصدار عقد / سند / فاتورة (القيمة من سجل الفاتورة) | العميل |
| توقيع العقد / السند | المسؤول |
| الموافقة / الاكتمال / الرفض (السبب فقط إن وُجد) | العميل |
| سداد الفاتورة | قالب جاهز فقط، غير مربوط بأي إجراء، ولا تُنشأ وظيفة سداد |

- أنواع الطلبات تظهر بالعربية بدل الاسم الداخلي.
- البريد الإداري القديم ذو المرفقات يُستبدل بالقالب الموحد.

## 6. القالب الموحد
- الشعار الرسمي الحالي، عنوان الحدث، جدول بيانات، زر إجراء، تذييل رسمي.
- ألوان #2A0E32 / #B99A55 / #FFFFFF / #FBFAF8، عربي RTL، مناسب للجوال.
- الأزرار إلى rifanss.com وتتطلب تسجيل الدخول؛ لا روابط مباشرة لمستندات خاصة.

## 7. الاختبار
- حساب عميل تجريبي، تنفيذ الدورة كاملة، التحقق من وصول كل رسالة مرة واحدة، إعادة الحفظ/الاستدعاء للتأكد من عدم التكرار، ومحاكاة فشل للتأكد من بقاء العملية وتسجيل الفشل.
- حذف بيانات الاختبار فقط، ثم تقرير بكل حدث ونتيجته.

## تفاصيل تقنية
- Migration: جدول `email_events` (id, event, entity_id, recipient_role, status pending/sent/failed/skipped, error, attempts, created_at, sent_at; UNIQUE(event, entity_id, recipient_role)); GRANT لـ service_role فقط؛ RLS بلا سياسات.
- Triggers AFTER INSERT/UPDATE على requests (إنشاء + تغيّر status عبر `IS DISTINCT FROM`)، contracts/promissory_notes (إنشاء + signed_at من NULL إلى قيمة)، invoices (إنشاء)، open_requests (submitted_at من NULL)، app_users (اكتمال التسجيل: انتقال الحقول الأساسية إلى مكتملة مرة واحدة) → `INSERT ... ON CONFLICT DO NOTHING` ثم `pg_net` POST إلى `/api/public/email-dispatch` مع سر داخلي (يُولَّد ويحفظ كـ secret ويُقرأ في القاعدة من vault).
- pg_cron كل 5 دقائق يستدعي نفس المسار لمعالجة pending/failed (attempts < 5).
- `src/routes/api/public/email-dispatch.ts`: يتحقق من السر، يحجز الصفوف (UPDATE ... status='processing' RETURNING)، يبني الرسالة من القاعدة بـ supabaseAdmin، يرسل عبر `sendMail`، يحدّث status/sent_at/error.
- `src/lib/rifans-mail.server.ts`: `renderRifansEmail({title, intro, rows, cta})`؛ `src/lib/email-events.server.ts`: خريطة الأحداث والقوالب (بما فيها invoice_paid غير مربوط).
- إزالة إرسال البريد القديم من notify-admin وProfileCompletionModal لتجنب الازدواج؛ لا تغيير على send-otp/verify-otp.
